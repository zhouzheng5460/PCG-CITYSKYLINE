# TownForge

把 [TownGeneratorOS](https://github.com/watabou/TownGeneratorOS)（Medieval Fantasy City Generator 的开源源码）改造成一个可交互编辑、并能导出 glTF/GLB 的城市生成器。

原项目是 Haxe + OpenFL 的桌面/Flash 风格 2D 生成器，算法写死在一次性 build 里、路宽是三个硬编码常量、没有任何导出能力。这个工程把生成内核逐文件移植到 TypeScript，在此之上加了三件事。

## 三个改造点

### 1. 禁建区：可绘制的"禁止创建内容"范围

支持矩形 / 圆 / 自由多边形三种画法。禁建区在三个层面生效，保证边界既精确又不会把城市搞散：

| 层面 | 做法 | 效果 |
| --- | --- | --- |
| 地块 | 计算地块与禁区交集面积占比，超过阈值（默认 35%，可调）整块标记 `blocked` | 整块地不生成任何内容 |
| 路网 | A* 建图时丢弃采样后落在禁区内的边（`edgeInsideZones`） | 路不会穿过禁区，但可以贴着禁区边界走 |
| 建筑 | 对每个建筑多边形做布尔差集（`polygon-clipping`） | 压线的建筑被精确切在禁区边界上 |

设计上有个关键取舍：**地块形状本身不裁剪**。早期版本用多边形布尔运算把地块切掉，结果城墙跟着变形、城门悬空、A* 直接无解。地块是城市的结构骨架，禁掉"内容"就够了 —— 边界精度交给建筑级裁剪来保证。

另外，禁区整块占用的地块**仍然参与 ward 随机分配**（只是最后不产出几何）。否则少一块地会让整条随机序列错位，城里其他所有地块的类型都会跟着变。

### 2. 路宽与拓扑点可编辑

原版的路宽其实是"地块内缩后留下的缝"，藏在 `Ward.MAIN_STREET / REGULAR_STREET / ALLEY` 三个常量里。改造后：

- 常量变成 `model.style` 参数，面板上可实时调主干道 / 街道 / 巷道三档宽度；
- `arteries` 从 `Polygon` 变成带 `width` 的 `Artery`，地块内缩量按**该边所属道路自己的宽度**计算；
- 点击任意一条路可以单独调宽（`widthOverrides`），渲染、导出、地块内缩三处同步；
- 打开"显示拓扑点"后可以直接拖拽路口顶点。拖动时只移动顶点并重绘（建筑暂时隐藏），松手后从坐标快照重建整个下游管线。

拖点后的重建不需要重跑 Voronoi：`Model` 被拆成 `buildPatches`（一次）和 `buildAll`（可重复），中间存一份顶点坐标快照，每次重建先复位坐标再跑。

### 3. GLB 导出

`buildTownMeshes()` 把模型转成 3D 网格，`exportGLB()` 手写 glTF 2.0 二进制（不依赖 three 的 exporter，Node 和浏览器都能跑）。

导出内容按语义分组命名，方便在 Blender / C4D / UE 里单独选中替换材质：

- `ground` 地面（城内）
- `street` / `street_edge` 主干道（按各自宽度成带，带深色路缘）
- `<ward类型>` 建筑，拆成 `_roof`（屋顶）和 `_wall`（墙面）两部分
- `wall` 城墙（按段生成后合并）+ 塔楼 + 城堡墙

坐标系：地图 `(x, y)` → 3D `(x, 0, y)`，高度沿 +Y，与 2D 编辑器俯视一致。

## 4. 现代城市：把"放什么"整层换掉

原来的内容层是 13 种中世纪 ward（行会、市场、教堂、贫民窟…），路面就是一条深色带。现在新增 `mode: 'modern'`，用一整套现代城市的内容层替换它——**底层空间链一个字没动**：

```
buildPatches()  →  Topology（顶点建图 + Dijkstra）  →  getCityBlock()（地块内缩）
        ↑                        ↑                              ↑
   Voronoi 分地块            拓扑寻路                    insetForEdge()
                                                                  ↓
                                                   道路横断面（同一函数推导）
```

关键约定：**道路中线就是地块边**，路宽就是地块内缩让出来的那道缝。所以横断面不是"另画一条路"，而是把这个缝隙按比例切成人行道 / 绿化带 / 车行道。这样路面、人行道、建筑红线永远严丝合缝，拖点或改路宽后自动跟着走。

### 4.1 道路：横断面 + 独立路口 + 标线

参考 [three-roads](https://github.com/vibe-stack/three-roads) 的"横断面 → 条带 + 独立路口几何"结构，但路口不手写，直接从路网图里读（度数 ≥ 3 的顶点）。

横断面按**比例**算，因为 1 世界单位 ≈ 7 m，写死米数没有意义：

| 部件 | 取法 |
| --- | --- |
| 人行道 | 红线宽 × 28%，clamp 到 0.16~0.5 |
| 绿化带 | 红线 > 1.5 时取 5% |
| 中央分隔带 | 仅主干道且红线 > 2.4 时取 4.5% |
| 车行道 | 余量，且保证 ≥ 红线的 42%（不够就先砍绿化带再砍人行道） |
| 车道数 | `2 × round(车行道 / 0.9)`，夹到 2~6；车行道 < 0.55 时降为单车道 |

路口是独立几何：车行道圆盘（`rIn = max(半车行) × 1.18`）+ 按方向锥开口的人行道转角环（`rOut = max(半总宽) × 1.02`）。边两端的条带用 `pad = r × 1.2` 截断，不斜插进路口。

标线分四层靠高度差避免 z-fighting：路面 0.012 / 绿化带 0.019 / 人行道 0.020 / 标线 0.032。主干道画双黄中心线 + 车道虚线（虚线 0.5 / 间隔 0.42），次干道画单白虚线，每个路口端画斑马线 + 停止线。

> 踩过的坑：路口人行道转角环如果"逐格交替 push 内外圈"，多边形会自交，earcut 会吐出横跨图形的黑色碎片。必须先把内圈连续走完再折回外圈。

### 4.2 土地用途：同心环 + 分位数

不是随机贴标签，而是按经验规律分区，再用**分位数**而不是绝对半径分档（这样 6 块地和 24 块地都能分出中心/中间/外围）：

| 分位 | 用途 |
| --- | --- |
| q < 0.18 | CBD（玻璃塔 + 裙房） |
| q < 0.42 | 商业（临主路） / 公共设施 / 住宅 |
| q < 0.72 | 住宅（临主路则商业） |
| q < 0.88 | 住宅 / 公园 / 地面停车 |
| 其余 | 工业 / 绿地 |

最后做**保底补位**：城里必须有 CBD、公园、地面停车、公共设施、工业各至少一个，缺哪个就从相邻档里换一块过来。半径基准是"原点到地块质心"，不能用 `model.center`（那是随种子漂移的参考顶点，第一版就因为它把十五块地全判成工业区）。

### 4.3 地块内容：先摆后裁

每个用途有独立规划函数，共同点是**建筑原型按世界坐标摆轴对齐矩形，再与可建区求交**，面积占比 < 52% 就丢弃。这样出来的楼永远规整、永远压在红线内：

| 用途 | 内容 |
| --- | --- |
| CBD | 7~13 层玻璃塔 + 1.3~2.2 层裙房 + 副楼 + 硬质铺装前场 |
| 商业 | 2~3 栋沿街板楼 + 后场停车 + 人行道铺装 |
| 住宅 | 行列式板楼 + 院通道 + 地面停车 + 绿地 |
| 工业 | 主厂房 + 混凝土堆场 + 货运停车 + 铁艺围栏 |
| 公共设施 | 主楼 + 前广场 + 树列 + 旗杆 |
| 公园 | 园路 + 交叉圆盘 + 喷泉 + 长椅 |
| 地面停车 | 沥青场地 + 车位阵列 + 绿化岛 |
| 绿地 | 草地 + 沿边林带 + 内部散树 |

凹地块的 `buffer()` 会返回自交多边形，这里做一次自身求交让它规范化（`intersect(ring, ring)`）；布尔运算全部走量化坐标，避免扫描线在近似共线处抛 `Unable to complete output ring`。

### 4.4 街网形态：从正交格网到张量场流线

现代模式的第一步（切地块）有四种形态，侧栏「布局」切换，只影响"怎么切"，切完都是同一份 `Patch[]`，后面的内缩 / 横断面 / 地块内容 / GLB 完全复用：

| 布局 | 做法 | 参考形态 |
| --- | --- | --- |
| 方格网 `grid` | 正交层级格网 + 低频正弦位移，格线索引决定道路等级 | 曼哈顿、芝加哥 |
| 场线 `field` | 格网整体过一个旋涡映射（扭转角 `amp·exp(-r²/2σ²)`），街道连续弯曲但格点对应关系不变 | 巴塞罗那扩展区 |
| 放射环 `radial` | 同心环 + 放射辐条，环半径带谐波起伏，可叠 `spiral·log(r/r_in)` | 华盛顿、堪培拉 |
| 张量场 `tensor`（默认） | 方向场 → 流线 → 平面图 → 面，见下 | RogueCities / symbios-tensor |

张量场这条链在 `src/town/field/`：

```
FieldSource[]  ──►  TensorField  ──►  traceFamily(主/次)  ──►  buildArrangement  ──►  Patch[]
(基准/边界/中心/禁区轮廓)   (无迹二阶张量)      (RK4 + Jobard–Lefer 播种)      (求交→半边→面)
```

几个关键决定：

- **必须是张量而不是矢量场**：街道方向无向，0° 与 180° 是同一个方向。用 `T = [cos2θ, sin2θ]` 累加再求主特征向量，θ 与 θ+π 天然等价，次方向自动成为正交方向。直接对角度做加权平均会把 0° 和 90° 平均成 45°。
- **场源配比**：全局基准（0.9）必须压住局部场源，否则次方向全部收敛到中心，整城退化成"环 + 辐条"。边界切向（半径 0.3R）、中心旋涡/放射（半径 0.34R）、禁建区轮廓（`path`）都只负责"把街道带弯"。
- **线距靠播种控制**：抖动网格撒种 + 每接受一条线就沿法向 ±spacing 补种（Jobard–Lefer），再跑两轮"扫描补洞"；与已有线贴合超过 45% 的候选直接丢弃 —— 这类平行孪生线会切出针尖碎面，碎面一丢就断网。
- **闭环要掐断**：旋涡场里流线会绕圈画回来，绕一圈就把城切碎。追踪时用网格哈希记录本线足迹，撞到 6 步以前的点即停。
- **共享顶点池**：求交后按 1e-3 量化建顶点池，相邻面拿到的是同一个 `Pt` 对象。`buildRoadNet` 靠对象身份配对两侧地块，所以不需要再焊接。
- **端点吸附（snap）**：线头常常停在另一条线旁差 1~3 单位的地方，那是度数为 1 的悬挂节点，路网会断开。把线头投影到邻近线段/轮廓上，让它变成 T 型连接。
- **补洞**：平面图偶尔漏一个面（顶点处共线退化），用"面的总面积 vs 轮廓面积"判断，少了就用布尔差补回来，且要求补出来的环顶点 100% 命中既有顶点 —— 否则补出一块对不上边的地，那条路只剩一侧，反而切断路网。

### 4.5 方向控制线：让街道顺着你画的线排

张量场唯一需要用户直接操作的东西。用户不需要理解张量，只要在图上画一条折线，意思是"这一带的街道朝这个方向排"：

```
FieldGuide(折线) ──► guideToSource() ──► type:'path' 场源 ──► 与基准/边界/中心一起合成
```

- **一条线管多宽**：影响半径 `0.26R`（约 3 个街区宽），`w = strength·exp(-(d/r)^1.6)`，在线两侧一个带内生效，离开带就退回全局基准方向。2D 上画成半透明蓝色宽带，就是这条半径。
- **强度为什么要 5 倍**：张量场在 2θ 空间做加权平均，两个方向合成后的角差会被"折半"。实测（基准 57.6°、线 18°）：权重比 1.2 : 0.9 时场只转到 32.5°，比 9 : 1 时仍有 2.7° 残差 —— 强度不够时用户会觉得"画了没反应"。5 倍（默认 strength 0.8 → 权重 4.0，约 4.4 : 1）把残差压到 5° 以内，同时保留指数过渡带。
- **回归测试量的是"路网走向 vs 线的夹角"**：带内所有路边按长度加权，夹角要**按 90° 折回**——张量场本来就产出两族正交街道，垂直那族不是错位。按 180° 折会把一半的边算成 90° 偏差，均值永远卡在 45°，看起来像"没生效"。
- **边界附近线会输**：轮廓那一圈街道必须顺着城界闭合，所以贴着 `0.85R` 往外画的线只能部分生效（实测城内 3.7°、外侧 14.4°）。这是形状约束，不是 bug。
- 方向线改的是**切块**（场 → 流线 → 面），所以必须整城重生；禁建区只是裁剪，两者走的是不同路径。

### 4.6 街道设施：按路布点

行道树和路灯不挂在地块上，而是沿主干道人行道中线布置（间距 2.5 / 5.0），灯臂朝向路心。硬上限 300 棵树 / 240 盏灯，改路宽或拖点后自动跟着路走。

### 4.7 一个 Scene，三个消费者

2D 编辑器、three.js 预览、GLB 导出读的是同一份 `Scene`（`src/scene/types.ts`）：

```ts
SurfaceFeature  { ring, mat, y }        // 地面/铺装/标线，按 y 从低到高铺
SolidFeature    { ring, y0, h, kind }   // 建筑体块，挤出 + 屋顶分材质
PropFeature     { kind, at, rot, scale} // 树/灯/长椅/喷泉/车…
PathFeature     { pts, width, mat }     // 内部道路、园路、围栏（可带高度成墙）
```

`Model.revision` 每次重建 +1，两个视图据此判断是否重建场景，不用手动通知。调色板集中在 `src/scene/palette.ts`，2D 用 `css()`，3D 用 `MAT[]`，不会出现"2D 看到的和 GLB 里不一样"。

导出分组：`ground` / `road/{surface,sidewalk,junction,marking}` / `lot/<用途>` / `street/{avenue,furniture,lighting}`。

## 跑起来

```bash
npm install
npm run dev        # http://localhost:5173
```

```bash
npm run test       # 53 次生成回归 + 确定性 + 重建幂等 + 禁建区 + 路宽 + 拖点 + 现代城市场景断言
npx tsx test/glb.test.ts   # GLB 结构校验 + 绕序自检 + 软件光栅化出图
npm run build      # 产物在 dist/
```

## 操作

| 操作 | 说明 |
| --- | --- |
| 滚轮 / 右键拖动 | 缩放、平移 |
| 点"矩形/圆/多边形"后拖拽 | 画禁建区（多边形双击闭合，Esc 取消） |
| 点"画方向线"后逐点点击 | 画方向控制线（双击结束，只影响张量场布局） |
| 勾选"显示拓扑点"后拖动圆点 | 改路网走向 |
| 点击道路 | 选中后单独调宽度 |
| 顶部"三维预览" | three.js 实时预览（和 GLB 同一套网格） |
| 顶部"导出 GLB" | 下载 `.glb` |

URL 参数可以复现状态：`?n=24&seed=12345&zone=1&verts=1&mode=modern&markings=0&furniture=0`。

侧栏里的开关直接控制场景内容：**风格**（现代城市 / 中世纪，切换会重跑整套生成）、**布局**（方格网 / 场线 / 放射环 / 张量场，只在现代城市下出现）、**道路标线**、**行道树 / 路灯**。关掉标线或设施后 2D 与 3D 会同步刷新，导出的 GLB 也按当前开关生成。

地址栏参数：`?layout=grid|field|radial|tensor`、`?mode=medieval`、`?n=24`、`?seed=8`、`?zone=1`、`?guides=1`（放两条示例方向线）、`?markings=0`、`?furniture=0`。

## 与原版的差异

逐文件对照翻译，几何算法、随机序列、难度参数都保持原样，同种子可以复现同一座城。有意的偏离只有四处：

1. `Polygon.buffer()` 里处理自交的循环，原版理论上可能死循环，这里没有改动逻辑但外层加了收敛保护；
2. `Ward.createOrthoBuilding()` 的 `while(true)` 加了 64 次迭代上限，超限返回原多边形；
3. 路宽从常量改为参数（默认值与常量一致：2.0 / 1.0 / 0.6）；
4. `Rng.reset` 对 seed ≤ 0 做了保护（原版 seed=0 时整个随机序列会退化为 0）。

原项目源码保留在 `../TownGeneratorOS-master/` 作为对照。

## 本次增强：GLB 导出体积优化

在 `src/export/` 内做了一组**不改变几何/外观**的导出压缩（不动生成算法，`buildTownMeshes` 的场景内容一致）：

- **索引按顶点数自动降位**：顶点 < 65536 的网格用 `Uint16` 索引（glTF `componentType=5123`），否则 `Uint32`。城市里绝大多数网格（尤其逐栋建筑）都落在 Uint16 区间，索引缓冲直接减半。
- **合并时顶点焊接**：`mergePrimitives` 之前只是拼接，相邻多边形共享边界会重复顶点。现在按「坐标量化 1e-4 + 法线量化 1e-3」把同位置同法线的顶点焊成一个 —— 整片路面/人行道（法线都是 +Y）收益最大。
- **合并时剔除退化三角**：焊接可能把极薄三角形塌成零面积，这类三角渲染不出却会触发绕序自检误报，按 `|cross|² ≤ 1e-18` 丢弃（与 `triangulate` 的 `DEGEN_AREA2` 约定一致）。

实测（种子 682063530，含广场，同一配置前后对比）：

| 配置 | 优化前 | 优化后 | 降幅 |
|---|---:|---:|---:|
| n=15 | 7.998 MB | 6.776 MB | −15.3% |
| n=24 | 9.836 MB | 8.303 MB | −15.6% |

三角形数与外观不变；`test/glb.test.ts` 新增「索引分量类型正确」与「顶点焊接：共享边合并 / 三角形数不变」断言。

## 5. Placemaker 桥接：把室外场地交给 128 个专业生成器

前面的地块内容（4.3）是手写的：8 种用途、8 个规划函数、共 169 行。公园就是"园路 + 圆盘 + 喷泉 + 长椅"，停车就是"沥青 + 车位阵列 + 绿化岛"。而 [Placemaker](../placemaker-master)（CS2 的一个场地设计 mod，GPL-3.0）有 **128 个 `[AreaGenerator]`**，每一个都是几千行专门做这件事的。

**但有一个反直觉的前提：Placemaker 不产建筑。** 它的 `ObjectRole` 枚举里只有树、灌木、长椅、路灯、车位、贴花这些，`Building` 在它代码里只作为"要避开的障碍物"存在。所以这不是"用 Placemaker 替换 TownForge"——那样会得到一座没有房子的城市。

它是个**纯室外场地设计器**。所以桥接管的是管线里的一个分叉：

```
切地块 → 路网横断面 → 用途分档 → 地块内容 ─┬─ 建筑体块      （TownForge 保留）
                                            └─ 室外场地      （Placemaker 接管）
                                                     ↓
                                          同一个 Scene → 2D / three.js / GLB
```

### 5.1 协议：一个 JSON，7 条通道

C# 端加了 `--emit`：

```bash
cd ../placemaker-core-lib
dotnet run --project Driver -c Release -- --emit cases/parking-150x100.json out/emit/plan.json
```

输入是"地块 + 临街"，输出是 Plan 的七条通道降到二维：`surfaces / nets / objects / areas / regions / zoning / paint`。CS2 特有的东西（`AssetRef`、`Control`、`Category`、`Upgrades`）全部丢掉——外部引擎一个都用不上。

**三条硬约定**（写在 `src/bridge/placemaker.ts` 顶部）：

| 约定 | 内容 | 搞错的后果 |
|---|---|---|
| 单位 | Plan 里一律是米 | Core 的 `MinArea` / `CheckReady` / `minApart` 全按米算，换算必须在**调用方**做，否则"这块地能不能跑"和"这块地多大"来自两套单位 |
| 坐标 | 平面是 `[x, z]` → `Pt(x, y)`，**哪个轴都不翻** | 翻一下就成镜像图，而且所有车位朝向都反了，很难一眼看出来 |
| 朝向 | `rot = yaw − π/2` | 3D 的 0 度朝 +Z，2D 画布 0 度朝 +X |

### 5.2 烘焙：浏览器里不能跑 dotnet

`tools/bake-plan.ts` 把整条链路走一遍：

```
Model(nPatches, seed)
  → patch[i].ward.getCityBlock()      可建区（已按相邻路宽内缩，与道路横断面同源）
  → 转米 + 平移到原点                  Placemaker 只认米，不关心世界坐标
  → patch.shape 每条边 → 一条街        "道路中线就是地块边"
  → dotnet PlacemakerDriver --emit    8~20 ms 的纯函数调用
  → src/bridge/data/*.plan.json       buildScene 读它
```

`src/bridge/data/*.meta.json` 单独存 `origin`（Plan 的 `(0,0)` 对应哪个世界坐标）。不塞进 plan 里，是因为 C# 端不知道"世界坐标"这回事，塞进去等于污染协议。

运行时只剩读 JSON：`buildScene(model, { placemaker: [{ plan, origin, patchIndex }] })`。同一个 Plan 的桥接结果按对象身份缓存（`WeakMap`），拖拓扑点时不会重算 24 遍。

### 5.3 车位：点必须重塑成线

Placemaker 的车位是**点**（CS2 里车位是 zone cell，不是对象），只有 `{x, z, yaw, scale}`。直接每个点画个方块会得到 276 个互相重叠的矩形。

实测两个性质让重塑变得简单：车位朝向只有 4 个值（0°/90°/180°/270°），同一朝向里垂直于排列方向的坐标只有少数几个值（一排一个）。所以：

1. 按 yaw 分 4 组 → 组内按垂直坐标聚类成排；
2. 排内按坐标排序，**相邻两车位的中点就是分隔线位置**——宽度不用猜，从间距直接得来；
3. 间距超过 1.6 个车位宽就切断（斜地块上轴对齐排会被边界切开，留下几十米空档）。

第 3 条是踩出来的：不切段的话，一条"前缘线"会横穿整块地把中间的车位排全划掉。第一版还有个更蠢的错——前缘线的两端放在了车的两侧而不是同一侧，结果每排都有一条斜穿地块的对角线。

### 5.4 结果

地块 #42，12491 m²，136.7 × 107.5 m 的梯形（张量场切出来的），46 条临街边：

| | TownForge 原有 | Placemaker 接管 |
|---|---:|---:|
| 车位 | 贴边排，无车道组织 | **276 个**（含 12 个 EV、6 个无障碍） |
| 车道 | — | 43 条主通道 + 2 条接驳车道，共 842 m |
| 出入口 | 无概念 | **2 个**（周长够长，自动分成入口 + 出口） |
| 绿化 | 沿边一圈 | 39 棵树 + 232 丛灌木 + 40 盏灯 |
| 三角形 | — | 7609（整城 175507 → 183116，**+4.3%**） |

挑地块的标准不是"最大的"，而是"最像一块正常开发用地的"：Voronoi 会产出 520 × 150 m
的长条带，面积不小，但 Placemaker 在上面只能沿边挤车位，拿它当样板会得出"桥接不行"的
错误结论。`tools/bake-plan.ts` 用 `紧凑度² × 面积适配度` 打分（目标 ~12000 m²）。

接驳车道会伸出地块 4 m 顶到路缘（`driveConnector` 的 `minZ = -4.00 m`）——这是对的，它就是来接街的。

### 5.5 绿地一族：一次烘 19 个

`--gens` 支持一批生成器跑在同一块地上，这样疏密可以横向对比（同一块地、同一把尺子）：

```bash
npx tsx tools/bake-plan.ts --patch 42 --gens park,campground,pond,formalGarden,...
npm run sheet      # out/bridge-sheet.png：20 格联系表，一眼看出哪些能用
```

联系表左侧三行、每格都写了自己的面/道具/路数。结论比数字重要：

| 生成器 | 面 | 道具 | 园路 | 判断 |
|---|---:|---:|---:|---|
| parking | 609 | 317 | 45 | 最完整，车位线是它独有的 |
| formalGarden | 50 | 304 | 35 | 对称园路 + 中央喷泉，读感最好 |
| communityGarden | 48 | 203 | 25 | 48 块菜畦 + 围栏，主题明确 |
| campground | 16 | 122 | 11 | 16 个帐篷平台，营地感强 |
| sportsPark | 3 | 66 | 16 | 两块场地 + 环形园路 |
| botanicalGarden / dogPark | 2 / 3 | 197 / 124 | 50 / 22 | 园路骨架清楚，细节靠道具 |
| park / greenwayPark / picnicGrounds / natureReserve | **0** | 129~366 | 12~24 | 只有园路和树，**完全不铺地面** |
| pond | 2 | 7 | 16 | 整块地变水面（见下） |
| polish*（8 个） | 0 | 0 | 0 | **单用没有任何输出**（见下） |

三个必须知道的坑，都是这一轮批量跑出来的：

**1）`polish*` 一族不能单独用。** 8 个全返回 `ready=yes` 但 0 面 / 0 道具 / 0 路。它们是"表面精修"层——只改**已有**地面的材质和贴花，而我们的输入是一个裸地块，没有父地面可供精修。它们的输入是 `SiteContext` 里的既有表面，不是自己的 `Plan` 输出。所以"polish 一族输入最简单，正好批量接"这个判断是错的，实测直接否掉。`test/bridge-green.test.ts` 把这个结论钉成了断言：哪天 Core 变了它们开始出东西，那条会炸出来提醒重新评估。

**2）绿地生成器不铺地面，桥接必须补草地底。** `park` / `greenwayPark` / `picnicGrounds` / `natureReserve` 的 `surfaces` 是**空的**——在 CS2 里地面就是地形，本来就长草，生成器只负责"往上画"。不补底的话桥接结果是一堆树漂在裸地上。

补底用的地块环不在 Plan 里（C# 端不知道世界坐标），烘焙时写进了 `meta.lotRing`，桥接时通过 `BridgeOptions.lotRing` 传进去，铺在最底层（比所有铺装低一档 `2e-4`）。铺装类生成器（parking / formalGarden / sportsPark）自己铺满整块地，草地被完全盖住，代价只是多一个和地块同形的多边形。

**3）`pond` 在 12.5k m² 的地上就是一个湖。** 实测水面 11983 m²，只留一个 100 m² 的小岛和一条园路。这不是桥接的问题，是这个生成器把"地块"整个当成水体——它适合小地块或需要配一个水面比例参数。

`bush → treeSmall` 的映射原来让"绿篱"变成一排小针叶树（formalGarden 的 197 丛灌木最明显）——这是 TownForge 道具种类的短板，已在 5.6 里补上。

### 5.6 样式层：让接进来的东西像 TownForge 自己的

几何对了不等于长得对。Placemaker 只给 `tree` / `bush` 这种粗角色，落到 TownForge 的道具库上还得挑对种类、挑对尺寸。这一轮改的是**呈现层**，生成算法一行没动。

**两个新道具种类：**

| 种类 | 尺寸 | 为什么要有 |
|---|---|---|
| `treeRound` | 冠 5.3 × 6.9 m，总高 9.9 m | `tree` 是细高的锥（11 m 的圣诞树），公园里几百棵站开像苗圃。阔叶冠才是"一公园的树"的读感。总高刻意和 `tree` 对齐，混种时不会看出两种身高 |
| `shrub` | 1.5 × 1.5 m，高 1.5 m | 原来没有灌木这一档，`bush` 只能借用 `treeSmall`（6.8 m 的小树）——一排绿篱看起来就是一排松树苗 |

**一张样式表，两个渲染器共用。** 2D 有两个渲染器：`render/svg.ts`（出图/测试）和 `ui/view2d.ts`（实时画布）。它们原来各写一份 `if (kind === 'tree' || ...)`，种类一多必然漂，更糟的是 `hedge` / `planter` / `fountain` **两个都不画**——Placemaker 接进来的花坛和喷泉在编辑器里直接消失。现在统一到 `scene/propStyle.ts`：

```ts
export const PROP_STYLE: Record<PropKind, PropStyle> = { … }   // Record 是刻意的：新增种类时 TS 直接报缺项
export function propDraw(p): PropDraw | null                   // "画点 / 画条 / 不画"的唯一判断点
```

**映射也改了两处：**

- `bush → shrub`（不再是 `treeSmall`）；
- `tree → 2/3 阔叶 + 1/3 针叶`，按树的序号轮换（`BridgeOptions.coniferRatio`，默认 1/3）。Placemaker 不区分树种，全画一种就丢掉了疏密变化。

**顺手修的自家不一致**：`green.shrubRatio: 0.25` 这个参数名写着"灌木占比"，长出来的却是 `treeSmall`。改成 `shrub` 之后，公园用途区的林下才真的有低矮一层（一个 24 块种子 8 的城市里 296 丛灌木）。这条分支只在"用途区 = 公园/林地"时才走到，默认城市里一片林地都没有，所以**视觉上普通城市没有变化**——`test/render.ts` 里加了 `city-park-zone` 这个 case 才测得到它。

**面数**：灌木 11 面（原来借小树是 18）、阔叶树 28 面（原来 `tree` 24）。接管地块 183138 → 181696，全城基线 **175507 一点没变**（生成层确实没被动）。

### 5.6.1 成排的灌木 → 绿篱（`bridge/hedge.ts`）

`shrub` 解决了"尺寸"，但没解决"形态"：Placemaker 在花园里是沿花床边线、按 3.3 m 节律排灌木的，一颗颗画成小锥，近看是一堆绿色碎块、远看是噪点。CS2 里那些点本来就表示**一条绿篱**。

**判据是 yaw，不是距离。** Placemaker 排绿篱时整条线共用一个 yaw（yaw 是这条线的**法向**，走向 = yaw + 90°），随手撒的时候每颗朝向都不同。实测 20 个生成器分得很干净：

| | 灌木数 | 用到的朝向档数（10° 分箱，上限 18） |
|---|---|---|
| `formalGarden` | 197 | **2** |
| `parking` / `natureReserve` / `park` / `dogPark` / … | 60~232 | 17~19 |

所以只靠"最近邻距离串链"是错的：那样 `natureReserve` 的散点能凑出 48% 的覆盖率，半片林地会凭空长出十几段绿篱。现在两道闸：

1. **整体闸** `yawSpreadMax`（默认 0.35）：朝向档数超过角度区间的 35% 就判定"随机旋转"，整份 Plan 一颗都不连；
2. **组内闸** `minYawGroup`（默认 3）：留下的朝向里，某一档至少 3 颗才算数。

过闸之后才按法向分桶（同一条线上必须共线）、沿线排序、按 8 m 间隔切段，每段出一根 `hedge`。段长写进 `PropFeature.len`，所以 3D 的盒子是真实长度（一条 12 m 的花坛边就是 12 m），不是固定的 4.2 m 小段。

实测 `formalGarden`：197 颗里 152 颗并成 **59 段、总长 410 m** 的绿篱框；其余 19 个生成器 0 段（`parking` 和 `natureReserve` 里各有 3~2 颗碰巧同向，被整体闸挡掉）。

**顺手修的一个真 bug**：`hedge` 的 `r` 是 0（它没半径、只有长度），而三个 2D 调用点都写成 `if (look.r <= 0) continue` 再做 `bar` 分支——绿篱在 3D 里有、在编辑器和导出的 SVG 里**从来没有出现过**。现在"2D 里怎么画"收进 `propStyle.ts` 的 `propDraw()` 一处，三个调用点共用，并且可以被断言直接测。

### 5.6.2 保留建筑：把楼喂进 `Obstacles`（`bridge/obstacles.ts`）

默认情况下 Placemaker 是"整块换掉"——旧建筑跟着消失。要"保留楼、只铺地面"，就得告诉它楼在哪：`SiteContext.Obstacles` 是一串**定向四边形**（A/B/C/D 四点 + `ObstacleKind.Building`），Core 在 `Composer.Compose` 末尾的 `SiteSafety.Apply` 里把压到地界的路、对象、铺装、区域、地形、粉刷全部**丢弃或裁开**。

```bash
npx tsx tools/bake-plan.ts --patch 90 --gens plaza,parking --keep
```

三点实现上的事：

1. **不能拿最小外接矩形糊过去。** TownForge 的体块轮廓有 4~7 个点（切角、L 形），实测 4 点轮廓的外接矩形平均就大 13%、最大差一倍——等于凭空封掉一块本来能用的地。现在 4 点原样传；多于 4 点先三角化，每个三角形补成四边形（第四点取 a-c 中点，落在边上，面积不变、也不会产生零长边）。
2. **单图层不走 composer。** `gen.Plan()` 只跑一个图层，`SiteSafety` 根本不在那条路径上——障碍物收下了却没人看（第一次烘出来的 `issues` 是空的，就是这么发现的）。驱动里把这一层包成 `ComposedPlan` 再补跑一次 `SiteSafety.Apply`，和游戏里同一行代码。
3. **`--keep` 只能烘焙时定。** 避让是生成时做的，运行时再改主意，铺装已经被裁掉了，楼一删就是一堆围着空气的空地。所以 `meta.keepBuildings` 写进烘焙件，`buildScene` 照着它保留体块。

**面积账**（patch 90，13123 m²，4 栋塔楼占 43%）：

| | 铺装 | 建筑 | 合计 | 压进建筑的重叠 |
|---|---|---|---|---|
| `plaza --keep` | 7072 m² (54%) | 5618 m² (43%) | **97%** | 0.00 m² |
| `parking --keep` | 7132 m² (54%) | 5618 m² (43%) | **97%** | 0.00 m² |

铺装 + 建筑 ≈ 地块面积，说明铺装真的被挖掉了楼那块；如果障碍物没生效，铺装会盖在楼底下、两项相加会到 130% 以上。这条账写成了断言（`test/bridge-obstacles.test.ts`），不靠看图。

**一个必须知道的语义**：`SiteSafety` 是"删"，不是"绕"。面积型生成器（`plaza` / 花园）表现很好——铺装贴着楼脚断开、树和长椅被摘掉；**路网型会被切坏**：`parking` 的 53 条车道最后只剩 1 条，因为车道横穿楼时整条被丢，不会改道。真要在这类地块上排车位，得先把地块按建筑切碎再逐块生成，那是另一件事。

### 5.7 已知限制

- **浏览器里跑不了 dotnet**，所以只能"烘焙 → 读 JSON"。要实时调参得另起一个本地服务（v2）；
- 已验证 31 个生成器（parking + 19 个绿地/花园类 + 5 个堆场/球场类 + 6 个铺装/商业类）+ 3 个 `--keep` 组合。`polish*` 一族**不能单用**（见 5.5），其余 100 多个还没试；
- 绿地一族的内容密度差距很大：`park` 出来只有一条环状园路 + 129 个点状道具，`formalGarden` 有完整的对称园路网。想要"设计感"就挑 garden 类，想要"野趣"就用 reserve 类；
- **绿篱是按边成段的**，花床四个角上有一段 1~2 m 的缺口——Placemaker 本来就没在角上放灌木，这里照实画，没有去补角；
- **保留建筑时路网生成器会被切坏**（见 5.6.2 末段）：避让语义是删除不是改道，`parking` 的车道会所剩无几。面积型生成器没这个问题；
- 斜地块上 Placemaker 偏好**沿边停车**，出来的排方向不规则（图见 `test/out/`）。这是它的布局策略，不是桥接的问题；
- `decals` 图层本身空转（s33 之后落叶改走地形贴图）；**但 `objects` 里的 `decal` 角色现在有用了**——球场的标线就是它，见 5.9；
- 堆场的道具只有三种造型（盒 / 桶 / 石堆），集装箱和托盘长得一样。要区分得给 `PropFeature` 加材质字段，这轮没做；
- **2D 出图只保证"面 + 大件"可读**：长椅 / 路桩 / 摊位 / 垃圾桶在整城视图里不到 1 px，按 `propStyle.ts` 的设计不画（3D 里都在）。所以市场广场的 47 个摊位在平面图上是一片空地，不代表没接；
- **台地是"每格抬到某个高度"，不是一张高度场**：Core 给的是 4 m 网格的独立环（`target` 一个数），桥接把每格出成带收顶的台体。相邻格高差 > 0.5 m 时接缝处是一道台阶——CS2 自己的 3.5 m 地形网格也是这么走的，所以照实画；想要顺滑得自己做插值，那就不是 Core 的数据了；
- **软件光栅化器（`test/soft3d`）不能用来判断亚米级细节**：0.18 m 宽的标线会画成虚线，贴地薄片的边缘会出锯齿孔洞。台地在 ±6 m 的特写下底部会看到白色小尖角，那是光栅化器的问题（同一窗口只画 `pm/terraform` 是干净的，650 个三角形最长边 5.47 m，没有瘦长片）。三角形列表本身是干净的 —— GLB 用的是同一批。判几何用数字，判观感用整城图；
- **`paint` 改底色要求强度 ≥ 0.8**：`abandonedLot --set subtype=demolished` 那种"整块地刷一层干草 @0.42"会被当成细节忽略，底色仍是草。想让它生效得调门槛，但那会连带改掉 `scrapyard` 的底色，所以先不动；

### 5.9 第一批「低面高物」生成器：堆场 / 废车场 / 跑道 / 球场

`carYard` `junkYard` `scrapyard` `runningTrack` `pitch` 五个。挑它们的理由是"面少物体多、接起来便宜"，实测正好相反：**它们的身份全在被老桥接整类丢掉的两条通道里。**

| 生成器 | 面 | 道具 | 其中贴花 | 接入后的判据 |
| --- | --- | --- | --- | --- |
| `carYard` | 16 | 809 | 0 | 泥土底色 + 箱/桶/废车；**0 张长椅** |
| `junkYard` | 17 | 717 | 0 | 同上（`paint` 刷了 213 块） |
| `scrapyard` | 3 | 509 | 113 | 铺装 + 17 块泥土补丁 + 113 件垃圾贴花不画 |
| `runningTrack` | 3 | 651 | 642 | 200 m 跑道 + 4 条分道线全部画出来 |
| `pitch` | 1 | 360 | 340 | 边线 / 中线 / 中圈 / 禁区弧全部画出来 |

**三个改动：**

1. **驱动器输出 `category`**（`Emit.cs`）。`Furniture` 是通用角色，Core 对它是**强制**要分类的（`RoleCategories.ForObject`），以前这个字段没写进 JSON，桥接只能一律当长椅。现在按分类查表：`industrial.wreck → car`、`industrial.barrel → barrel`、`rock → rock`、`industrial.* → crate`（新道具种类，1.1 m 的灰盒子）；查不到的也走 `crate` —— 宁可多一个盒子，不要多一排长椅。
2. **贴花 → 标线**（`DECAL_MARKING`）。球场白线是沿线每隔 1.5 m 撒的一串 `decal`，只有点位和朝向。按分类给尺寸、摊成 1.7 m 的窄条（比 1.5 长 0.2 m，让相邻两条**重叠**而不是对接——对接在细线上会渲染成一串虚线）；整场贴花（68 × 52.5 m 半场纹理）只画外框，铺成实心面就是一块白板。
3. **`paint` 决定地块底色**。`carYard` 的铺装只占 21%，其余 79% 是 Core 刷出来的泥土（`layer 3 @ 0.85`，覆盖整块地）。改成土色之后才读得出"这是堆场"，而且**一个面都不多**。

**新增道具种类三个**：`crate` 12 面 / 1.1×1.1×0.9 m、`barrel` 20 面 / 0.64×1 m、`rock` 12 面 / 1.8×0.7 m。堆场单块地 +10964 三角形（809 件 × 12 面），全城 175507 → 186471（6.2%）。

**踩到的坑**：`bake-plan.ts` 单块地时临时文件名没有 `.whole` 后缀，而收尾按 `pieces` 重新拼路径 —— `--gens` 批量烘焙直接 ENOENT。现在按实际落盘的路径记录。

### 5.10 第二批「铺装/商业」生成器：商场 / 商铺 / 市场 / 废弃地块

`stripMall` `outdoorMall` `shopsPark` `mallPark` `abandonedLot` `marketSquare` 六个。

这一批绊住的都不是画法，是**协议里的三处空白**：

**1）商场和市场族不自己找门 —— 整块地被拒绝。**

第一次 emit 直接返回 `surf=0 net=0 obj=0`，`readyKey = …Step.PlaceEntrance|…Reason.NeedsEntrance`。Core 源码把理由写得很直白：

> The player places them on the outline; nothing is suggested and Build waits for a way in for cars.

也就是说 Placemaker 把"门在哪儿"当成**玩家的决定**，不是它的。自动城市里没有人替它放门，这三个生成器就永远不产出。处理方式是在烘焙工具里补一个（`autoEntranceMarkers`）：

- **只在被拒绝时补**。已经 ready 的 25 份输出必须逐位不变，而公园族的 `entrance` 是**步行**门、和车行门不是一回事，给它们塞门会改掉已有布局；
- 位置取**最长的那条临街边中点**（地块环的每条边都对着一条街），kind 用停车场族的 `entrance`（双向车行门，商场族与市场族都认）；
- 只给 `at` 给点，不给 `segment`/`t`：切碎地块时环是子块的环，和 `streets` 的索引根本不是一回事，少一层"索引对不上"的风险；
- 结果记进 meta 的 `autoEntrance`，读数据的人知道"这块地的门是工具放的"。

**2）`zoning` 是"留给建筑的地"，不是可以丢的通道。**

`stripMall` 铺装只占 30%，剩下的 27%（3341 m²）是 `EU Commercial Low` 宗地 —— 那块地在 CS2 里是用来长商铺的，**本来就不铺**。以前整类丢掉，于是整块地读成「草坪 + 角落里一个停车场」，看着像规划失败。

现在把宗地四边形铺一层砾石（`pm/zoning/<zoneId>` 分组）。砾石在这里的意思很明确：场地平整过、等着盖，既不像草坪（以为没规划过）也不像广场（以为已经能用）。高度压在铺装之上、草地底之下。

| 生成器 | 铺装 | 宗地 | 合计 | 实体 |
| --- | --- | --- | --- | --- |
| `stripMall` | 3693 (30%) | 3341 (27%) | **56%** | 265 |
| `outdoorMall` | 10114 (81%) | 1992 (16%) | **97%** | 162 |
| `shopsPark` | 3943 (32%) | 2352 (19%) | **50%** | 113 |
| `mallPark` | 8185 (66%) | 1159 (9%) | **75%** | 300 |
| `marketSquare` | 12420 (99%) | 0 | **99%** | 356 |
| `abandonedLot` | 88 (1%) | 0 | **1%** | 258 |

`abandonedLot` 的 1% 是对的：默认 subtype 是 `overgrown`（"一块长满草的空地"），Core 的区域标签就是 `green` + `core`。

**3）分类表漏项，错在最显眼的地方。**

| 分类 | 数量 | 以前 | 现在 |
| --- | --- | --- | --- |
| `bollard` | 162 | 1.1 m 灰盒子 | 路桩（市场广场的路桩排成列，是那个广场的秩序） |
| `ruins.wall` | 7 | 灰盒子 | **残墙**（新道具，3.2 m 长条 —— 一块废墟不能是一堆方盒子） |
| `ruins.rubble` | 30 | 灰盒子 | 石堆 |
| `centerpiece.statue` | 1 | **蓝色水盘** | **雕像**（新道具，基座 + 人像） |

中心物是一块地的视觉焦点，错了比旁边几十棵树错了更刺眼。

**新增道具种类两个**：`ruinWall` 12 面 / 3.2×0.28×1.1 m、`statue` 24 面 / 基座 2.4 m 见方。`test:shops` 钉了 60 项，重点是**反向断言**：本来 ready 的生成器不许被塞门（`markers.given === 0`）、宗地与铺装的并集重叠必须 < 2%、以及"门真的传进了 Core"（不靠"恰好 ready"）。

**顺手加的烘焙参数**：`--set k=v,k2=v2` 覆盖生成器设置，`--tag x` 给同地块同生成器的变体加后缀。验证过 `abandonedLot --set subtype=demolished`（walls 7→1、rubblePiles 0→6，说明参数真的生效），但它整块地刷的是 `layer 1 @0.42`，达不到改底色的 0.8 门槛 —— 这一条记在已知限制里。

### 5.11 台地：`terraform` 从「贴地薄板」变成有体积的台体

`terraform` 以前是整类当**铺装面**处理的：每个环铺一层土色面，按数组序号抬 0.2 mm。
三个后果，最后一个是致命的：

1. 2.6 m 高的垃圾堆和 0.3 m 高的格子长得一模一样（都只是一块平地）；
2. 65 块薄板叠在同一条地上只差 0.2 mm，深度缓冲上是必然的 z-fighting；
3. 摆在这些堆上的箱子、油桶还站在 y≈0，堆一抬起来就全埋进土里。

**第一个坑：高度不在顶点里。** `Emit.cs` 的 `Ring()` 走 `Vec3`，只写 x/z —— 但 `terraform`
的顶点高度恰恰只在 `Ring[i].y` 里（`AiTerrain.Cells` 用它做羽化斜坡）。于是先补了
`hs` 数组。补完发现**堆场的 `hs` 全是 0**：这些环根本没有坡度，高度在 `target` 里。

这直接决定判据怎么写。第一版写的是「顶点和 target 差多少」，全零的环被判成
「坡度 0 m、target 2.6 m」→ 画出来高度 0，**料堆原地消失**（`skipped 65/65`）。
正确的判据是**顶点之间的极差**：极差 > 5 cm 才逐顶点用，否则整块按 `target` 抬平。

**第二个坑：台体画出来，道具就埋了。** 抬起来的格子上摆着 76 件道具（`carYard`），
台体一立起来它们就在土里。`PropFeature` 因此加 `baseY`，两个来源取大的那个：

- `o.y`：Core **自己给的高度**（`scrapyard` 194/509、`carYard` 96/809 带这个字段，
  数值与 `target` 一一对得上：2.6、4.0、0.3）。这是权威值，桥接以前整类丢掉了；
- 按台地环自己查：Core 没给的那些（占多数），在「中心 + 半径 0.5 m 的四个探针」上
  取**最高**的那一格。只查中心的话，压在格子边界上的东西会拿到低的那格，然后被邻居的
  2 m 墙面从中间劈开；取最高只会让它略微悬空 —— 悬空看得见，劈开看不见。

**第三个坑：4 m 的格子装不下 4.8 m 的废车。** 侧面直上直下时，车就悬在崖边上。
`terraceSolid` 因此支持**收顶**（顶面朝形心缩进 `高度 × 0.45`，最多 40%），
坡从地面爬上来接住它。

实测（p42，12491 m²）：

| 生成器 | 台地 | 最高 | 被抬的道具 | 场面 |
|---|---|---|---|---|
| carYard | 65 格 | 2.6 m | 76 / 809 | 泥土底 + 一堆堆废料，料堆上压着废车和油桶 |
| junkYard | 83 格 | 2.6 m | 69 / 717 | 同上 |
| scrapyard | 52 格 | 4.0 m | 138 / 396 | 4 m 高的废钢堆 |
| pond | 1 座岛 | 0.3 m | 7 / 7 | 岛的 `raise` 成台体，`lower` 不补水面（已有 `surfaces.water`） |

`lower` 只在**没有真水面**时才补一层水面：TownForge 的地面是一整块平面，没有
「挖坑」这回事，减出来的高度只能靠水面表达；园池本来就铺了 water 面，再补一层
就是永远被挡住的死几何（`pond` 的面数因此从 4 掉到 3）。

## 已知限制

- 禁建区如果整个盖住城市中心，广场会被放弃（城市仍能生成，只是没有中央集市）；
- 拖动顶点不校验地块自交，把顶点拖过对边会得到扭曲的地块；
- 城墙高度、塔楼尺寸目前是固定值，没有开放为参数；
- 现代模式的路口只有"圆盘 + 方向锥开口"一种形态，没有做渠化岛 / 转向车道；
- 建筑是体块级（没有窗、阳台、屋顶设备），靠屋顶 / 墙面分材质来分区；
- 大规模城市（`n=40`）导出约 2.5MB，浏览器端导出仍在 1 秒内完成（本次已进一步压缩约 15%，见上节「GLB 导出体积优化」）。
- Placemaker 桥接只能离线烘焙（浏览器无法调 dotnet），实时调参需要本地服务；已验证 31 个生成器（parking + 19 个绿地/花园类 + 5 个堆场/球场类 + 6 个铺装/商业类），`polish*` 一族不能单用，见 5.5。
